GUÍAS DE CONEXIÓN · B · TOOLS POR MCP · S4

Qué tan difícil es poner las tools del cliente detrás de nuestra puerta.

La integración B es más sencilla cuando las herramientas ya se exponen como servicios con contratos estables. Es más compleja si están dentro del proceso del agente, usan credenciales propias o pueden ejecutarse fuera del Gateway.

Esta página documenta escenarios de integración y arquitectura objetivo, no una certificación de compatibilidad ni esfuerzo medido en jornadas. Ver en paralelo la guía C de identidad ↗

B añade control sobre la ejecución, no solo sobre la intención.

Con A, la plataforma inspecciona los tool_calls vistos en inferencia. Con B, el agente invoca las tools desde {gateway}/mcp, usando su agent_token, y la puerta evalúa la ejecución real antes de llamar al target.

1 · AgenteDeclara tools y ejecuta MCP
2 · PuertaAutorización, reglas, aprobación y evidencia
3 · TargetLambda u OpenAPI en el MVP
01 · EXPOSICIÓN

¿Dónde vive la tool?

Una Lambda o API OpenAPI es más fácil de registrar que una función local de Python.

02 · INVOCACIÓN

¿El agente usa MCP?

Debe consultar tools/list e invocar tools/call contra el Gateway, no usar una ejecución directa alternativa.

03 · CONTROL

¿Quién tiene los permisos?

IAM, API keys, OAuth, conectividad y bypass determinan cuánto hay que rediseñar.

Ruta de menor fricción: API OpenAPI o Lambda bien delimitada, autenticación soportada, endpoint accesible y agente que puede utilizar MCP. La ruta difícil suele exigir extraer lógica, delegar credenciales y restringir acceso directo a recursos.
Alcance real de nuestro MVP: la decisión D-03 contempla targets Lambda y OpenAPI. Amazon Bedrock AgentCore Gateway admite otros tipos —MCP remoto, API Gateway nativo, entre otros—, pero no debemos presentarlos como ya soportados por nuestro producto. Las capacidades de interceptación y aprobación se validan mediante SP-01, SP-04 y SP-05. Decisión D-03 ↗

AWS · SERVIDOR MCP

AgentCore Runtime o ECS con MCP remoto

MVP pendiente

El agente ya utiliza un cliente MCP y el servidor de tools funciona por HTTPS.

Facilita
Protocolo y herramientas remotas disponibles.
Brecha
El tipo MCP remoto está disponible en AgentCore, pero excede D-03 del MVP.
Pasos concretos
  1. Inventariar tools, esquemas, versión MCP y credenciales del servidor remoto.
  2. Para el MVP actual, adaptar a Lambda/OpenAPI o formalizar ampliación para MCP remote target.
  3. Redirigir el cliente MCP a la puerta; comprobar nombres, herramientas visibles y errores.

API Gateway REST + Lambda / ECS

Baja–media

Lambda utilizada como tool

Baja–media

AWS · ACCESO DIRECTO

Agente ECS con boto3 a DynamoDB / S3 / RDS

Alta

El Task Role del agente permite actualizar recursos directamente sin un servicio de herramientas.

Facilita

Brecha

HÍBRIDO · SISTEMA CRÍTICO

ERP privado, OAuth delegado y operaciones irreversibles

Alta

Las herramientas ejecutan pagos, transferencias o modificaciones sensibles mediante APIs privadas.

Facilita
Puede existir una API corporativa con contrato estable.
Brecha
Red privada, credenciales por usuario, reintentos e idempotencia.
Pasos concretos
  1. Diseñar conectividad privada o front-end autenticado para que la puerta alcance el target.
  2. Configurar IAM/API key/OAuth downstream según el target; C no delega automáticamente la credencial del usuario al ERP.
  3. Prevenir operaciones duplicadas y validar SP-04/SP-05 antes de prometer HITL real extremo a extremo.
AWS · Conectividad VPC egress ↗

Escenario de mayor esfuerzo: el agente conserva acceso directo.

Ejemplo AWS: un agente en ECS ejecuta una actualización con boto3 contra DynamoDB. Publicar la misma acción como tool MCP no elimina los permisos de escritura que ya posee su Task Role.

↓
DynamoDB · UpdateItem

La plataforma no controla la ejecución; el agente puede modificar el recurso sin pasar por MCP.

Después · ejecución gobernada
ECS · agente cliente MCP
↓
Puerta · Cedar, registro y aprobación
↓

Es necesario retirar al agente los privilegios de bypass si se necesita control obligatorio.

Límite del producto: el cierre del bypass de red e IAM es responsabilidad del cliente (CTRL-25). Solo gobernamos las tools cuya ejecución pasa realmente por la puerta. La disponibilidad de una tool MCP no demuestra que sus rutas alternativas hayan desaparecido.

Contrato y pruebas de aceptación

La conexión B usa el mismo token del agente en ambos canales; si existe C, la identidad del usuario se reenvía también en MCP. El cliente debe usar exactamente los nombres que expone la puerta: <target>___<tool>.

POST {gateway}/mcp
Authorization: Bearer gov_AGENT_TOKEN
X-Gov-User-Token: JWT_USUARIO_OPCIONAL
Content-Type: application/json

{"jsonrpc":"2.0","id":1,"method":"tools/list"}
{"jsonrpc":"2.0","id":2,"method":"tools/call",
 "params":{"name":"pedidos___cancelar_pedido",
           "arguments":{"pedido_id":"123"}}}

Solicitudes JSON-RPC ilustrativas para versiones MCP anteriores a 2026-07-28; los métodos son llamadas distintas, no dos objetos enviados juntos. La revisión 2026-07-28 tiene metadatos y descubrimiento diferentes. Véase versiones MCP soportadas por AWS ↗. La operación y sus argumentos son ficticios.

  • Tool aprobada: la llamada llega al target, la respuesta se registra y los datos personales se filtran según política.
  • Tool denegada: en modo activo la respuesta MCP usa isError: true y el target no se ejecuta.
  • Tool requiere aprobación: devuelve PENDING_APPROVAL y el resultado depende de la implementación y validación de SP-04/SP-05.
  • B parcial: la cobertura registra cuántas tools declaradas por el agente pasan por MCP; las demás quedan fuera del perímetro.
Abrir S4 · Ejecución por MCP en la consola ↗
B y C son independientes. Con A+B sin C, la plataforma puede gobernar ejecución por agente (solo_workload), pero no atribuirla a un usuario verificado. En Preset 2, ciertas operaciones de escritura necesitan C; una operación crítica con aprobación humana personalizada necesita además la identificación del usuario. Ver guía C ↗
1 · EnrutamientoEl agente invoca la tool del Gateway por MCP y su nombre coincide con el declarado al modelo.
2 · Bloqueo efectivoDenegar tools/call impide que el target ejecute; no se limita a ocultar la respuesta.
3 · Perímetro verificableSe identifican tools fuera de la puerta y se restringen rutas alternativas cuando se exige exclusividad.
