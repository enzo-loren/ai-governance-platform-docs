Identidad del usuario

Comparación de arquitecturas reales, compatibilidad de tokens, pasos de conexión y criterios de aceptación por solicitud.

GUÍA DISPONIBLE · S3 · IDN-01
CONEXIÓN C · IDENTIDAD DE USUARIO

Primero, tres preguntas.

C agrega a la conexión A el JWT de un usuario humano en X-Gov-User-Token. Si existe B, debe propagarse también al canal MCP. El token del usuario nunca reemplaza al agent_token.

01 · PERSONA

¿Hay un usuario humano?

Un proceso programado puede seguir como solo_workload sin inventar una identidad humana.

02 · TOKEN

¿Hay un access token JWT apropiado?

Debe ser verificable y estar destinado al recurso autorizado. Una cookie o cualquier ID token no basta.

03 · PROPAGACIÓN

¿Llega el token hasta el agente?

El backend debe mantener el contexto de cada sesión y enviar el JWT correcto en cada llamada a inferencia y MCP.

Escenario de menor fricción: IdP OIDC existente + access token JWT correcto + backend que lo propaga. Si falta alguna condición, el trabajo se desplaza hacia la configuración OAuth, la delegación o la federación.

AWS · SERVERLESS

Cognito User Pools + API Gateway + Lambda

Baja*

Una aplicación autenticada con Cognito invoca una API que valida JWT antes de llegar a la Lambda del agente.

Ya existe
IdP OIDC, JWT firmados y JWKS públicos.
Brecha
Conservar el JWT original y comprobar su audiencia para gobernanza.
Pasos de integración
  1. Verificar que la ruta utiliza un access token y no un ID token. API Gateway puede entregar claims aunque no se conserve el JWT original.
  2. Configurar un recurso/audiencia autorizado para gobernanza. Cognito permite resource binding desde su endpoint OAuth de managed login; no es automático en todos sus SDK.
  3. Mapear cognito:groups a roles y reenviar el token original en cada solicitud del agente.

AWS · CONTENEDORES

ECS / EKS con Auth0, Keycloak u otro OIDC

Baja–media

El agente corre en contenedores, y la aplicación utiliza un IdP externo para autenticar a cada persona.

Ya existe
Autenticación OIDC independiente del runtime AWS.
Brecha
No confundir IAM del pod/task con el usuario; revisar audience y scopes.
Pasos de integración
  1. Confirmar que el proveedor emite un access token JWT aceptable para la API de gobernanza.
  2. Propagar el token a lo largo del backend hasta la llamada al modelo y, si se usa B, a /mcp.
  3. Configurar en la plataforma el emisor, clientes permitidos y mapeo de grupos a roles.
IETF · Perfil JWT de OAuth access tokens ↗
AWS · LOAD BALANCER

ALB authenticate-oidc + ECS / EC2

Media

ALB autentica al usuario antes de entregar la petición a una aplicación detrás del balanceador.

Ya existe
x-amzn-oidc-data con claims firmados por ALB.
Brecha
Ese JWT es una assertion de ALB, no el access token OIDC esperado por C.
Pasos de integración
  1. Verificar la firma y el ARN del ALB si el backend confía en sus claims.
  2. Obtener por un flujo OAuth controlado un access token JWT con destino autorizado; no reenviar ciegamente x-amzn-oidc-data.
  3. Si se evalúa x-amzn-oidc-accesstoken, comprobar formato, audience y verificabilidad: el encabezado no está firmado por ALB y puede contener un token opaco.
AWS · ALB OIDC headers ↗
AZURE · IDENTIDAD CORPORATIVA

Microsoft Entra ID + App Service / Functions

Baja–media

Una aplicación empresarial utiliza Entra ID y su backend llama a un agente por cuenta del usuario.

Ya existe
IdP OIDC, access tokens y permisos delegados.
Brecha
El token recibido puede estar destinado solo a la API de origen.
Pasos de integración
  1. Registrar la API de gobernanza como recurso de destino, con scopes delegados apropiados.
  2. Cuando se recibe un token para la API intermedia, evaluar On-Behalf-Of (OBO) con MSAL para obtener otro token destinado a gobernanza.
  3. Propagar el token resultante; mapear grupos/roles mediante los claims realmente emitidos y probar consentimiento, expiración y renovación.
Microsoft · OAuth On-Behalf-Of ↗
GOOGLE CLOUD · APP WEB/MÓVIL

Identity Platform / Firebase + Cloud Run

Media

El frontend autentica personas con Firebase/Identity Platform y el backend verifica su ID token.

Ya existe
Identidad humana y un ID token JWT verificable.
Brecha
El ID token tiene como audiencia el proyecto Firebase, no nuestra API.
Pasos de integración
  1. Continuar validando ID tokens Firebase para autenticar al usuario en su backend; no enviarlos directamente como access tokens C.
  2. Diseñar un flujo OAuth/OIDC o intermediario confiable que emita un access token JWT apropiado para la audiencia de gobernanza.
  3. Conservar la asociación entre uid, usuario, permisos y token delegado en cada llamada del agente.
Google · Firebase ID tokens ↗
GOOGLE CLOUD · ACCESO PROTEGIDO

IAP + Cloud Run / GKE

Media–alta

IAP valida el acceso a una aplicación y entrega una assertion JWT firmada sobre la solicitud.

Ya existe
x-goog-iap-jwt-assertion y claves públicas propias de IAP.
Brecha
La assertion identifica el acceso a IAP y su audiencia no corresponde a gobernanza.
Pasos de integración
  1. Validar la assertion del lado cliente contra el JWKS específico de IAP y su audiencia real.
  2. Intermediar hacia un token delegado compatible con C; no reutilizar la assertion de IAP como access token de la plataforma.
  3. Probar el vínculo entre usuario autenticado, backend y petición emitida por el agente.
Google Cloud · IAP signed headers ↗
HÍBRIDO · LEGACY

SAML / Active Directory / cookies de sesión

Alta

La aplicación conoce al usuario en su servidor, pero no puede presentar un access token JWT admitido por C.

Ya existe
Login empresarial o sesión del servidor.
Brecha
Falta emisión OIDC/OAuth con audiencia para gobernanza.
Pasos de integración
  1. Evaluar federar el IdP SAML a un proveedor OIDC. Cognito User Pools puede actuar como puente SAML→OIDC.
  2. Para sesiones por cookie, incorporar un authorization server o broker de identidad; no tratar la cookie como JWT.
  3. Definir mapeo de usuario, grupos, expiración, revocación y trazabilidad entre aplicaciones.
AWS · Federación SAML con Cognito ↗
MULTICLOUD · WORKLOAD

IAM Role / Managed Identity / Service Account

No aplica / alta

Un agente batch en Lambda, ECS, Azure Functions o Cloud Run se autentica como servicio, sin persona originadora.

Ya existe
Identidad de máquina para recursos cloud.
Brecha
Es diferente de una identidad humana. Si no hay usuarios, C no es necesaria.
Pasos de integración
  1. Para procesos autónomos, declarar tiene_usuarios_humanos = false y operar con A y opcionalmente B como solo_workload.
  2. Si también atiende personas, llevar identidad por usuario desde un IdP de la aplicación; IAM de servicio no sustituye ese contexto.
Contrato del proyecto · principal solo_workload ↗

El contrato que finalmente debe cumplir el agente

Estas cabeceras son las mismas para un backend ejecutado en Lambda, ECS, Azure Functions o Cloud Run. La conexión A es obligatoria; C es opcional y puede cubrir solo parte de las solicitudes.

Solicitud hacia la puerta

POST {gateway}/inference/v1/chat/completions
Authorization: Bearer gov_AGENT_TOKEN
X-Gov-User-Token: ACCESS_TOKEN_JWT_USUARIO
X-Gov-Trace-Id: UUID_OPCIONAL

Con B activa, incluir también X-Gov-User-Token en POST {gateway}/mcp. Cada usuario y cada solicitud requieren su propio contexto; no almacenar un token global compartido en el agente.

Validación y resultados esperados

  • Con JWT válido: verificar firma/JWKS, emisor, expiración, tipo de token y cliente/audiencia configurada; mapear usuario y grupos a roles.
  • Sin cabecera: continuar como solo_workload, sin simular una persona.
  • JWT inválido: responder 401 gov_user_unauthorized o degradar con alerta según configuración.
  • C parcial: medir solicitudes con JWT válido respecto del tráfico total del agente.
Ver contrato canónico ↗
Decisión de diseño pendiente: el contrato actual acepta client_id o aud configurados. Para tokens destinados a recursos downstream conviene exigir audience/resource binding explícito; validar solo un cliente conocido no prueba que el token se emitió para esta API. Esta página propone ese criterio de seguridad, pero no afirma que ya esté implementado. Véase RFC 9068.

Checklist para una reunión de discovery técnico

Antes de estimar esfuerzos o prometer una integración directa, verificar estas dependencias con el equipo de identidad y con el dueño del agente.

1. Proveedor y flujo¿Qué IdP y qué grant OAuth usa la aplicación?
2. Tipo de token¿Es un access token JWT verificable, no un ID token, assertion o cookie?
3. Destinatario¿Se puede emitir con audience/recurso y scopes adecuados?
4. Claims de identidad¿Qué claim identifica al usuario y cómo se obtienen roles/grupos?
5. Propagación segura¿El backend conserva el vínculo usuario–solicitud hasta la llamada al agente?
6. Pruebas de rechazo¿Qué pasa con firma alterada, expiración, emisor o audiencia distintos?
